# feature-planner 스킬

하나의 feature를 "아이디어"에서 "개발 가능한 이슈 단위"로 변환하는 파이프라인.
기반 문서: `docs/features/feature-planning-workflow.md`

## 전제 조건

스킬 시작 전 확인:
1. `docs/features/{name}/spec-original.md` 가 존재하는가?
   - 없으면 사용자에게 먼저 작성을 요청하고 중단한다.
2. `{name}` 은 사용자가 명시했는가?
   - 없으면 "어떤 기능인가요? (docs/features/ 아래 디렉터리 이름으로 쓸 식별자를 알려주세요)" 로 확인한다.

---

## 전체 흐름

```
spec-original.md (초기 아이디어)
    ↓ 단계 1 — 요구사항 인터뷰
spec-fixed.md (확정된 요구사항)
    ↓ 단계 2 — PRD 작성 + 기술 결정(ADR)
prd.md (단일 기준 문서)
    ↓ 단계 3 — 이슈 분해
issues.md + GitHub Issues (실행 가능한 작업 단위)
```

---

## 단계 1: 요구사항 인터뷰

### 목적
초기 기능 정의서의 모호성을 제거하고, 엣지 케이스와 결정 사항을 확정한다.

### 입력
- `docs/features/{name}/spec-original.md`
- 코드베이스 (기존 구조·패턴 참조)

### 실행 방법

`spec-original.md` 와 코드베이스를 읽은 뒤, **아래 8개 영역**을 하나씩 질문한다.
한 번에 하나씩만 묻고, 각 질문에 추천 방식과 이유를 함께 제시한다.

1. 이 기능의 primary user는 누구인가?
2. 최소 동작 시나리오 3개는? (가장 기본적인 사용 흐름)
3. 데이터 저장 방식 — 기존 구조와의 관계는?
4. 경계 조건 — 최대값, 빈 값, 중복, 동시성은?
5. 에러 처리 — 실패 시 사용자에게 어떻게 표시하는가?
6. 기존 UI 패턴과의 일관성 — 어떤 컴포넌트를 재사용할 수 있는가?
7. 성능 제약 — 허용 응답 시간, 데이터 크기 제한은?
8. 향후 확장 가능성 — 이 결정이 다음 feature에 영향을 주는가?

인터뷰 과정에서 등장하는 핵심 용어를 **Ubiquitous Language** 로 고정한다.
(코드·문서·대화에서 동일 단어로 동일 개념을 가리킨다)

### 산출물
모든 질문이 끝나면 `docs/features/{name}/spec-fixed.md` 를 작성한다.
spec-fixed.md 에 "용어 정의" 섹션을 반드시 포함한다.

```
[GATE] 사용자가 spec-fixed.md를 읽고 확정할 때까지 대기.
"spec-fixed.md를 확인해주세요. 확정되면 '단계 2 진행'이라고 말씀해주세요." 라고 안내 후 멈춘다.
```

## 단계 2: PRD 작성 + 기술 결정(ADR)

### 목적
요구사항·디자인·기술 결정·범위를 하나의 문서로 통합해 단일 기준점을 만든다.

### 입력
- `docs/features/{name}/spec-fixed.md`
- `docs/features/{name}/design.md` (존재하면 참조)
- 코드베이스 (기존 패턴 참조)

### 2-1. PRD 뼈대 생성

기술 결정 섹션은 TODO로 비워두고 나머지를 먼저 작성한다.

PRD 구조:
- **개요** — 기능의 목적과 범위
- **사용자 스토리** — 사용자 관점의 흐름
- **기술 결정** — (TODO — 2-2 이후 채움)
- **Out of Scope** — (TODO — 2-4에서 채움)
- **용어 정의** — spec-fixed.md의 Ubiquitous Language 동기화

### 2-2. 아키텍처 3안 제안 & 비교

코드베이스를 분석해 **최소 3가지 구현 안**을 제안한다.
아래 **7가지 고정 기준**으로 비교표를 작성한다:

| # | 기준 | 설명 |
|---|------|------|
| 1 | 데이터 구조 | 어떤 형태로 데이터를 저장/표현하는가 |
| 2 | API 레이어 변경지점 | 기존 API에서 무엇이 바뀌는가 |
| 3 | 상태관리 변경지점 | Context/Store에서 무엇이 추가되는가 |
| 4 | 핵심 동작 | 이 기능의 가장 중요한 동작이 어떻게 구현되는가 |
| 5 | 컴포넌트 구조 | 어떤 컴포넌트가 추가/수정되는가 |
| 6 | 기존 패턴과의 일관성 | 코드베이스의 기존 관습과 얼마나 맞는가 |
| 7 | 테스트 용이성 | 단위 테스트, E2E 테스트 작성이 쉬운가 |

```
[GATE] 사용자가 3안 중 하나를 선택할 때까지 대기.
"위 3안 중 하나를 선택해주세요." 라고 안내 후 멈춘다.
```

### 2-3. ADR 작성

선택된 안을 PRD "기술 결정" 섹션에 아래 4요소로 작성한다:

```markdown
### 기술 결정 제목

**Context** — 이 결정이 필요한 맥락. 무엇을 풀고 있는가.
**Decision** — 무엇을 선택했는가.
**Alternatives** — 거부한 안과 각각의 거부 이유. (이유 없는 거부 금지)
**Consequences** — 트레이드오프. 장점뿐 아니라 단점도 반드시 명시한다.
```

### 2-4. Out of Scope 작성

"하지 않을 것"을 구체적으로 나열한다. 명시하지 않으면 구현 범위가 확장된다.

```
[GATE] 사용자가 Out of Scope를 읽고 확정할 때까지 대기.
"Out of Scope를 확인해주세요. 확정되면 '단계 3 진행'이라고 말씀해주세요." 라고 안내 후 멈춘다.
```

### 산출물
- `docs/features/{name}/prd.md`

---

## 단계 3: 이슈 분해

### 목적
PRD를 실행 가능한 작업 단위(GitHub Issues)로 변환한다.
각 이슈는 독립적으로 TDD 사이클을 돌릴 수 있어야 한다.

### 입력
- `docs/features/{name}/prd.md`

### 수직 슬라이싱 원칙

> "이 이슈만 완료하면 사용자에게 보여줄 수 있는 동작이 있는가?"

- **Yes** → 수직 슬라이스. TDD 사이클을 돌릴 수 있다.
- **No** → 다른 이슈와 합치거나 다시 나눈다.

**수평 슬라이싱(레이어별: API → Context → UI)은 금지.**
마지막 이슈까지 완료해야 동작이 나오므로 TDD 사이클을 이슈 단위로 돌릴 수 없다.

### 이슈 크기
- 반나절~하루 안에 TDD 사이클(Red→Green→Refactor) 완료 가능한 것
- 너무 크면 피드백 루프가 느려짐, 너무 작으면 PR 오버헤드가 초과

### 의존성 순서
- 앞 이슈의 결과가 다음 이슈의 입력이 되도록 배치
- 역방향 개발 금지

### Acceptance Criteria — Given-When-Then 형식

각 이슈에 AC를 반드시 포함한다:

```markdown
## Acceptance Criteria
- [ ] Given [사전 조건], When [행동], Then [기대 결과]
- [ ] Given [사전 조건], When [행동], Then [기대 결과]
```

AC는 이후 테스트 시나리오의 씨앗이 된다.

```
[GATE] 사용자가 이슈 목록을 읽고 수직 슬라이스 기준 충족을 확인할 때까지 대기.
"이슈 목록을 확인해주세요. 수직 슬라이스·AC·의존성 순서가 맞으면 'GitHub 등록'이라고 말씀해주세요." 라고 안내 후 멈춘다.
```

### GitHub 등록 (사용자 승인 후)

```bash
gh issue create --title "이슈 제목" --body "설명 + AC + 의존성"
gh project item-add <PROJECT_NUMBER> --owner <OWNER> --url <ISSUE_URL>
```

### 산출물
- `docs/features/{name}/issues.md`
- GitHub Issues (각 이슈에 AC 포함)
- 프로젝트 칸반 보드 Todo 컬럼에 배치

---

## 승인 게이트 요약

| 지점 | 확인 내용 | 다음 단계 진행 신호 |
|------|----------|--------------------|
| 단계 1 후 | spec-fixed.md — 모호성 제거, 용어 확정 | "단계 2 진행" |
| 단계 2-2 후 | 3가지 안 비교 — 사용자가 안을 선택 | 안 번호 선택 |
| 단계 2-4 후 | Out of Scope — 범위 확정 | "단계 3 진행" |
| 단계 3 후 | 이슈 목록 — 수직 슬라이스, AC, 의존성 순서 | "GitHub 등록" |

**게이트에서 사용자 응답 없이 다음 단계로 절대 진행하지 않는다.**
