# 태그 기능 PRD

> 참조: spec-fixed.md | 작성일: 2026-06-02 | 상태: 초안

---

## 개요

노트 앱에 태그(Tag) 기능을 추가한다. 사용자는 노트를 편집하는 화면에서 태그를 자유롭게 추가·삭제할 수 있으며, 태그는 노트 저장 시 함께 서버에 반영된다.

이번 스펙의 목표는 태그 **입력·저장·표시** 핵심 흐름을 완성하는 것이다. 필터·검색·목록 표시는 다음 스펙으로 분리한다.

---

## 사용자 스토리

| # | As a… | I want to… | So that… |
|---|-------|------------|----------|
| 1 | 노트 작성자 | 노트에 태그를 추가하고 싶다 | 노트를 주제나 맥락으로 분류할 수 있다 |
| 2 | 노트 작성자 | 태그를 chip 형태로 시각적으로 확인하고 싶다 | 현재 어떤 태그가 붙어 있는지 한눈에 파악할 수 있다 |
| 3 | 노트 작성자 | Enter 또는 `,`로 태그를 빠르게 추가하고 싶다 | 마우스 없이 태그 입력 흐름을 끊지 않을 수 있다 |
| 4 | 노트 작성자 | 잘못 추가한 태그를 chip의 × 버튼으로 삭제하고 싶다 | 원하지 않는 태그를 정리할 수 있다 |
| 5 | 노트 작성자 | 태그 변경 사항이 저장 버튼 클릭 시에만 반영되길 원한다 | 실수로 태그를 바꿔도 저장 전에 되돌릴 수 있다 |
| 6 | 노트 작성자 | 대소문자가 다른 중복 태그가 조용히 무시되길 원한다 | 의도치 않은 중복 태그 없이 깔끔하게 관리할 수 있다 |

## 기술 결정

> 아키텍처 안 B 채택 — `useTagEditor` 커스텀 훅 + Controlled TagChipList

### ADR-01. 태그 저장 방식 — 노트 문서 내 배열 vs 별도 태그 테이블

**Context**

백엔드는 `json-server`가 `db.json`을 파일로 서빙하는 단순 구조다. 별도 엔드포인트(`/tags`)를 만들 수는 있지만 관계형 조인이나 트랜잭션을 지원하지 않는다. 현재 스펙에서 태그는 노트에 종속되어 있고, 전역 태그 관리(이름 변경·통계)는 Out of Scope다.

**Decision**

`Note` 문서 안에 `tags: string[]` 배열로 내장(embed)한다. 태그를 독립 엔티티로 분리하지 않는다.

**Alternatives**

- **별도 `/tags` 엔드포인트**: 태그를 정규화된 엔티티로 관리. 전역 이름 변경·자동완성에 유리하지만, json-server 수준에서 관계 무결성을 보장할 수 없고 현재 스펙 범위를 초과한다.
- **쉼표 구분 문자열**: `tags: "react,typescript"` 로 저장. 파싱 비용이 생기고 타입 안전성이 떨어진다.

**Consequences**

- (+) API 변경 없음 — `updateNote`의 `Partial<Note>` 시그니처가 이미 `tags`를 수용한다.
- (+) 노트 단위 CRUD와 완전히 동기화된다.
- (−) 태그 전역 수정·중복 집계는 클라이언트에서 전체 노트를 순회해야 한다(향후 스펙에서 해결).

### ADR-02. 태그 중복 판정 기준 — 대소문자 무시 vs 대소문자 구분

**Context**

사용자가 `"React"`와 `"react"`를 별개 태그로 인식할 가능성이 낮다. 저장 형태는 사용자가 입력한 대소문자를 그대로 유지하되, 추가 시점의 중복 판정만 별도로 처리해야 한다.

**Decision**

추가 시 `toLowerCase()` 비교로 중복을 판정하고, **저장은 처음 입력된 형태 그대로** 유지한다. 중복 판정 시 에러 메시지 없이 입력창만 비운다(조용한 무시).

**Alternatives**

- **대소문자 구분**: `"React"`와 `"react"`를 별개 태그로 허용. 사용자 혼란을 유발할 가능성이 높다.
- **소문자 강제 정규화**: 입력 즉시 `toLowerCase()` 적용. 일관성은 높아지지만 `"JavaScript"` 같이 대소문자가 의미 있는 태그명을 덮어쓴다.

**Consequences**

- (+) 사용자가 의도한 표기(대소문자)를 보존하면서 실수 중복을 방지한다.
- (+) `useTagEditor` 훅 안에 판정 로직이 고립되어 단위 테스트로 쉽게 검증할 수 있다.
- (−) 저장된 태그 배열에 `["React", "react"]`가 공존할 수 없으므로, 향후 서버 데이터 마이그레이션 시 주의가 필요하다.

### ADR-03. 태그 저장 시점 — 즉시 저장(Autosave) vs 명시적 저장(Save 버튼)

**Context**

현재 `NoteEditor`는 title·content를 저장 버튼 클릭 시 일괄 PATCH한다. 태그를 조작할 때마다 즉시 PATCH하면 취소 버튼이 태그에 작동하지 않아 title·content와 저장 시점이 어긋난다.

**Decision**

태그 변경은 `useTagEditor` 훅의 로컬 상태로만 관리하다가, **저장 버튼 클릭 시 title·content·tags를 단일 PATCH로 일괄 전송**한다.

**Alternatives**

- **태그 조작 즉시 PATCH**: 태그 변경 손실이 없지만, 취소 버튼이 tags에 작동하지 않아 UX 불일치가 발생한다(안 C에서 기각된 이유).
- **태그 전용 저장 버튼**: title·content 저장과 독립적으로 태그를 저장. 저장 진입점이 2개로 늘어나 UX가 복잡해진다.

**Consequences**

- (+) 기존 title·content 저장 흐름과 완전히 동일하여 사용자 멘탈 모델을 깨지 않는다.
- (+) 취소 시 태그도 함께 되돌아가 예측 가능한 동작을 보장한다.
- (−) 저장 전 앱을 닫거나 새로고침하면 태그 변경이 소실된다(title·content와 동일한 정책).

### ADR-04. 컴포넌트 아키텍처 — useTagEditor 훅 + Controlled TagChipList

**Context**

태그에는 중복 판정·15자 제한·trim·Enter/쉼표 감지 등 여러 비즈니스 규칙이 있다. 이 로직을 컴포넌트 내부에 두면 UI와 결합되어 단위 테스트가 어렵고, NoteEditor가 비대해진다.

**Decision**

`useTagEditor(initialTags)` 커스텀 훅이 모든 태그 상태와 비즈니스 로직을 캡슐화하고, `TagChipList`는 props만 받는 controlled 컴포넌트로 분리한다.

```
useTagEditor(initialTags)
  └─ { tags, addTag, removeTag }

NoteEditor
  ├─ const { tags, addTag, removeTag } = useTagEditor(initialTags)
  └─ <TagChipList tags={tags} onAdd={addTag} onRemove={removeTag} />
        ├─ NoteTag × n  (× 버튼 포함)
        └─ TagInput      (Enter·쉼표 감지)
```

**Alternatives**

- **TagInput에 로직 내장(안 A)**: 컴포넌트가 상태와 규칙을 모두 보유. 재사용·테스트 어려움.
- **Context에서 조작(안 C)**: 태그 로직이 전역 상태에 혼입, 저장 시점 불일치 발생.

**Consequences**

- (+) `useTagEditor`를 `renderHook`으로 독립 단위 테스트할 수 있다.
- (+) `TagChipList`·`TagInput`이 순수 컴포넌트라 props만 바꿔 스토리·테스트 작성이 쉽다.
- (+) NoteEditor는 훅 호출과 컴포넌트 배치만 담당해 title·content 처리 방식과 대칭을 이룬다.
- (−) `useTagEditor.ts` 파일이 하나 추가된다.

## Out of Scope

### NoteList / NoteItem 태그 표시

노트 목록(사이드바)에서 각 노트의 태그를 chip으로 표시하는 기능은 이번 스펙에 포함되지 않는다. 목록에 태그를 렌더링하면 시각적 밀도가 높아져 별도 UI 검토가 필요하며, 우선 NoteEditor에서 핵심 흐름을 검증한 뒤 다음 스펙에서 다룬다.

### 태그 기반 필터링

특정 태그를 선택해 해당 태그가 붙은 노트만 표시하는 필터 기능은 이번 스펙에 포함되지 않는다. 필터 UI(사이드바 내 태그 패널 혹은 드롭다운)와 클라이언트 측 필터 로직은 태그 입력·저장 흐름이 안정화된 이후에 독립 스펙으로 분리한다.

### 태그 기반 검색

검색창에서 태그명을 입력해 노트를 찾는 기능은 이번 스펙에 포함되지 않는다. 전문 검색(Full-Text Search) 혹은 인덱스 기반 태그 조회는 백엔드 구조 변경을 수반할 수 있어 별도로 설계한다.

### 태그 자동완성 / 추천

이전에 사용한 태그를 드롭다운으로 제안하거나 자동완성하는 기능은 이번 스펙에 포함되지 않는다. 전체 태그 목록을 집계하는 API 또는 클라이언트 캐시 전략이 추가로 필요하다.

### 태그 이름 전역 수정 / 병합

특정 태그명을 전체 노트에 걸쳐 일괄 변경하거나, 두 태그를 하나로 합치는 기능은 이번 스펙에 포함되지 않는다. 태그를 독립 엔티티로 관리하는 데이터 모델 변경이 선행되어야 한다.

### 태그 색상 / 아이콘 커스터마이징

태그에 색상이나 아이콘을 지정하는 기능은 이번 스펙에 포함되지 않는다. 현재 디자인 시스템에 태그별 시각적 식별 체계가 정의되어 있지 않으며, 데이터 구조에도 색상 필드가 없다.

### 태그 개수 상한 설정

노트 한 개에 붙일 수 있는 태그 개수에는 제한을 두지 않는다. 향후 성능 문제나 UX 이슈가 확인되면 그 시점에 제한값을 도입한다.

### 태그 공유 / 협업

다른 사용자와 태그를 공유하거나 공동 편집하는 기능은 이번 스펙에 포함되지 않는다. 현재 앱에 사용자 인증·권한 체계가 없다.

### 오프라인 / 동기화

태그 변경 사항의 오프라인 저장 및 재연결 시 동기화는 이번 스펙에 포함되지 않는다. 앱 전체의 오프라인 지원 전략이 결정된 이후에 함께 다룬다.

## 용어 정의

> 확인 후 내용을 채워 주세요.

| 용어 | 정의 |
|------|------|
| 태그(Tag) | 노트에 붙이는 짧은 문자열 레이블. `tags: string[]` 배열로 저장되며 노트를 주제·맥락별로 분류하는 데 사용한다 |
| Chip | 추가된 태그를 시각적으로 표현하는 UI 요소. 태그명과 × 버튼으로 구성된 작은 둥근 배지 형태이며, × 버튼은 호버 시에만 노출된다 |
| 확정 저장 | 저장 버튼 클릭 시 태그 변경 사항이 title·content와 함께 PATCH 요청으로 서버에 일괄 전송되는 시점. 저장 전 변경은 로컬 상태에만 존재한다 |
| 낙관적 업데이트 | API 응답을 기다리지 않고 로컬 상태(메모리)를 먼저 갱신한 뒤 UI에 즉시 반영하는 패턴. 이 앱에서는 CRUD 성공 후 리페치 없이 `setNotes(prev => ...)` 로 직접 갱신한다 |
